CleverERP · frontend architecture

reusable screens that load in sections

I refactored CleverERP’s frontend around a reusable approach to everyday interactions, helping screens load in stages and keeping repeated code easier to maintain.

my contribution
Frontend architecture and refactoring
built with
Ruby on Rails, Hotwire

the challenge

In an ERP, a lot of daily work happens in lists: finding a record, narrowing the results, opening a form, and checking what changed. CleverERP has those interactions across users, purchasing, and its product and process library.

I wanted a consistent experience across those screens and less repeated work behind them. As the application grew, building each interaction separately meant more places to maintain the same behavior.

keep the work moving

The page takes shape while its tables load asynchronously. From there, people can narrow a list, work with a record, and see their changes reflected without reloading the whole screen.

My goal was to make those everyday interactions feel familiar wherever someone was working in the application.

inside the process library

The Process Library is one place this approach comes together. People can narrow a list of options and manage records from the same screen.

the decisions behind it

make common interactions reusable

I brought repeated frontend behavior into a shared approach, so improvements could carry across screens and new features could build on what was already there.

let the page arrive in stages

Tables load independently of the surrounding page. That lets the screen appear before all of its content is ready. I haven’t measured a before-and-after speed improvement.

choose conventions that fit the product

I took an opinionated approach within Rails, shaped around CleverERP’s recurring workflows. It gives the application a consistent foundation, with the tradeoff that developers need to learn and maintain those shared conventions.

what this makes possible

The approach is used across user management, the Process Library, and purchasing. These screens share familiar interactions while still serving different kinds of work.

For me, the value of keeping code DRY is having fewer places to maintain the same behavior. This refactor gave CleverERP a more reusable foundation to build on as the product grows.
